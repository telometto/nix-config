# CrowdSec investigation and health

Blizzard uses CrowdSec for local HTTP/SSH detection, a Traefik bouncer for
HTTP enforcement behind Cloudflare Tunnel, and an INPUT-only firewall bouncer
for host traffic. The firewall bouncer does not inspect forwarded MicroVM
traffic and does not replace the MicroVM isolation or WireGuard policy.

## What the data means

Open **CrowdSec investigation** in Grafana. Its first four panels show:

- Source IP, target host, decision origin and reason for blocked requests.
- Local detections with source country/ASN and supporting event counts.
- Individual blocked requests, with paths, methods, User-Agent and decision ID.
- Fail-closed operational denials, separately from detected malicious traffic.

A community decision's scenario is the reason that source was banned. It is
not proof that the corresponding request attempted that attack against this
host. Country/ASN appear on local alerts where CrowdSec supplied them; they
are not invented for request records without enrichment. The numeric panels
show acquisition, parsing, scenario activity, active-decision inventory and
bouncer polling. An inventory count is not an attack count.

The patched Traefik plugin sends aggregate origin/remediation/IP-version
metrics to LAPI. List origins use `lists:<scenario>`. This fixes the upstream
1.4.5 plugin's omission of decision origin. Individual source IPs and paths
are kept in local logs, not in metric labels or the bouncer usage payload.
The Console's behavior inference remains a server-side feature; it may still
show unknown behavior for decisions that it cannot classify. Its resource
savings figures remain estimates. Historical unknown counts cannot be repaired
by changing future reporting.

## Implementation

- `packages/crowdsec-bouncer/` pins upstream 1.4.5 and vendors no new dependency.
  The patch preserves decision metadata alongside the original cache action.
  It emits a structured `crowdsec_remediation` event only when the bouncer
  applies a remediation, and separates operational denials from decisions.
  Allowed responses restore the original response writer, while remediation
  paths forward streaming and WebSocket response-writer interfaces. Metric
  reports are serialized, retried without discarding counts, and
  acknowledge only the submitted snapshot so concurrent requests are retained.
- `hosts/blizzard/security/traefik.nix` loads that immutable local plugin.
  No public response marker is used as evidence: events are generated by the
  bouncer itself, so application `403`s and supplied headers cannot masquerade
  as a block merely by using the same status/header.
- `hosts/blizzard/security/crowdsec.nix` acquires SSH journals as syslog and
  Traefik journals as message-only JSON. `target_host` uses `target_fqdn`
  for log detections and the request host for AppSec observations.
  A prerequisite service removes obsolete hash-named Nix context links while
  preserving administrator-owned files and the current generation's links.
- `crowdsec-alert-archive` polls a bounded recent alert window once per minute
  and advances an incremental cursor with a small overlap. Its durable UUID
  ledger avoids routine re-export. Queries exceeding 500 alerts are split into
  smaller time windows, oldest first. At one second or less, the complete
  window is fetched without a count cap, preserving alerts sharing a timestamp.
  Relative CLI filters include a 45-second latency margin; local filtering
  keeps only the intended interval. Dense windows can therefore use more memory
  than a normal page. Each completed window is committed, and interrupted sweeps
  resume their saved interval before starting a new sweep. A crash between
  emission and commit can replay an alert;
  use `alert_id` to identify it. It does not copy raw event payloads.
- The bouncer's 256-entry queue drops security records rather than blocking
  requests when journal output stalls. Failed drop-report attempts retain the
  accumulated count, including concurrent losses. A later request retries the
  `crowdsec_remediation_log_drop` report after queue capacity returns. Pending
  events and counts are in memory and are lost on restart. Inspect these reports
  in the Traefik journal: Alloy's two-event allowlist does not forward them to
  the investigation dashboard, and its WAL cannot recover pre-journal losses.
- Alloy reads only the Traefik and alert-archive journals, then forwards only
  the two structured security event types. Regular access logs are discarded.
  Event timestamps retain the original detection/enforcement time.
  A local WAL supports delivery recovery; the initial journal read is limited
  to 24 hours. This is not an off-host forensic archive or an exactly-once log.
- VictoriaLogs listens on `127.0.0.1:9428`; Grafana accesses it through its
  backend. Retention is 90 days with a 10 GiB disk retention target and 5 GiB
  free-space reserve. The size target deletes older daily partitions; it is
  not a strict quota for a sudden burst within the newest partitions.
- Grafana alerts cover unavailable collectors, HTTP ingestion stalls while
  Traefik is busy, elevated parsing failures, stale bouncer polling, archive
  failures, log delivery drops, full storage, and operational denials.

The projection excludes query strings, authorization headers, cookies and raw
payloads. Paths and User-Agent can still contain personal data; Grafana access
must remain restricted. The plugin bounds individual text fields. Local alert
context already shared with CrowdSec Console is controlled by the existing
console-sharing settings, separately from this local archive.

## Detection rollout and rule maintenance

AppSec listens only on `127.0.0.1:7422`, using the existing Traefik bouncer
credential. The initial rollout loads `crowdsecurity/appsec-virtual-patching`
in **observation mode**. It inspects URLs and an allowlist of non-credential
headers, not request bodies; authorization, cookies and access assertions are
not copied to the AppSec request.
Matching requests are allowed; `CancelEvent()` prevents follow-on scenario
bans while `SendAlert()` retains the WAF observation. The archive labels these
`appsec_observation`, and a separate Grafana table shows them without claiming
that they were blocked. Context uses the AppSec request's host, method and path
(the path excludes its query string). Request dumping is not enabled.

AppSec connection failures and HTTP 500 responses fail open for this observation
rollout. Existing IP decisions remain enforced. Other AppSec protocol errors
can still cause a plugin denial; those remain operational errors. The AppSec
stall alert detects a busy proxy with no inspection activity. Body inspection
and inline blocking need separate Matrix federation, OIDC, upload, streaming,
IPv4/IPv6 and direct-header-spoof acceptance before promotion. Do not simply
change `default_remediation`: promotion must also review the observation hooks,
the archive's observation label, and attribution of inline WAF blocks.

Global CrowdSec simulation is disabled, so all installed scenario remediations,
including the four `crowdsecurity/http-dos` scenarios, are active enforcement.
AppSec remains a separate observation-only path. Review the resulting local
alerts and decisions against normal Matrix sync, application APIs and crawler
traffic before changing this policy.

Local IP remediation now increases from 4 hours in 4-hour steps to a maximum
of 24 hours, based on retained decisions for that IP within the last 168 hours.
This is decision history, not a lifetime offender count; database retention
bounds it, and retained imported/manual decisions can also affect the count.

The daily `crowdsec-update-hub` timer refreshes the catalogue, prints an upgrade
preview and checks installed item status. An available upgrade deliberately
fails the check with exit code 2 so Grafana reports **CrowdSec rules need
maintenance**; network/check failures also require attention. It does not
replace rules or restart the engine. The upstream reload-after-index-refresh
is disabled because this NixOS service does not implement reload.

For a reviewed upgrade on Blizzard:

1. Inspect `journalctl -u crowdsec-update-hub.service` and
   `cscli hub upgrade --dry-run`. Review changed rules and custom/tainted items.
1. Take a root-only backup/snapshot of `/etc/crowdsec` and
   `/var/lib/crowdsec`, including rule data and symlink targets. Hub content is
   mutable state; a NixOS generation rollback alone does not restore it.
1. In a maintenance window, run `sudo cscli hub upgrade` without `--force`.
   Find the generated configuration path in `systemctl show crowdsec -p ExecStart`
   and validate it with the running package's `crowdsec -c <path> -t` as the
   `crowdsec` user before restarting. Do not restart after a failed validation;
   restore the saved rule state and validate again.
1. Restart CrowdSec only after validation, then verify acquisitions, both bouncer
   pulls, AppSec observations and application availability. Re-run
   `sudo systemctl start crowdsec-update-hub` to clear the maintenance alert.

Grafana uses the existing Pushover route for AppSec observations and selected
local exploit/authentication detections. Simulated DoS detections and imported
blocklist hits do not trigger that detection notification. Notification delivery
still needs a live acceptance check.

Application-specific authentication collection from Gitea, Matrix/MAS and
Pocket ID remains pending representative redacted failure/success log samples
and verified original client IPs from those VMs. Their logs are not present in
Blizzard's host journal. No guessed parser, broad network listener, additional
blocklist subscription or blanket CAPTCHA policy is enabled by this rollout.

## Validation

```bash
nix build .#checks.x86_64-linux.crowdsec-observability --no-link
nix build .#checks.x86_64-linux.crowdsec-http --no-link
```

The new flake check validates effective source/enforcement/scrape contracts,
context-link ownership, safe alert projection, and pure plugin regression
checks. The GitHub workflow also runs three socket fixtures outside the Nix
build sandbox:

- `tests/crowdsec_bouncer_runtime.py`: actual pinned Traefik/Yaegi, a synthetic
  LAPI, blocked and allowed clients, attributed usage metrics, outage denials,
  and query-string exclusion.
- `tests/crowdsec_appsec_runtime.py`: real isolated CrowdSec, production observation
  hooks/context, retained matching alert without an IP ban, and ban-duration
  escalation capped at 24 hours.
- `tests/crowdsec_logs_runtime.py`: actual pinned Alloy/VictoriaLogs, effective
  processing configuration with file input replacing journal input, exclusion
  of unrelated records, and Grafana investigation and notification queries.

These fixtures use only local synthetic traffic. They do not prove deployment,
real client attribution through Cloudflare, kernel packet drops, live journal
permissions, Grafana UI rendering or Console ingestion.

## Deployment acceptance

After an explicitly approved Blizzard deployment:

1. Check `crowdsec-contexts`, `crowdsec`, `crowdsec-firewall-bouncer`, `traefik`,
   `alloy`, `victorialogs` and the alert-archive timer. Confirm no stale-context
   warnings and no local-plugin interpreter errors.
1. Check `cscli metrics` and `cscli bouncers list`. SSH acquisition must be
   present after SSH events; both bouncers must have recent successful pulls.
   Check the firewall's INPUT chains/sets for both IP versions. Do not treat
   a registered key or a running unit as proof of packet enforcement.
1. Perform the IPv4/IPv6 and direct-header-spoof tests in
   [the HTTP acceptance runbook](crowdsec-http-detection.md). Verify the new
   event source matches the known client. Repeat Matrix availability probes.
1. In a controlled test window, apply a short-lived decision for a dedicated
   test client. Confirm a block event with the correct source, target, origin
   and reason appears in Grafana, then verify expiry/removal restores access.
   Test host firewall blocking separately without using the management client.
1. Confirm local alerts appear with target host and, when available, country/ASN.
   Check data survives service restarts. Verify the log-delivery and health
   alerts and the existing notification route actually deliver notifications.
1. Check Console remediation origin categories after its ingestion delay.
   New attribution does not backfill historic aggregate counts or turn inferred
   community intent into observed local attack evidence.
